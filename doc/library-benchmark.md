# 图库性能测量

先构建生产页面，再运行一档图库：

```sh
npm run build
npm run benchmark:library -- --size=10000
npm run benchmark:library -- --size=50000
```

脚本不在 CI 中执行。`--smoke` 使用 200 张图片和 10 张导入图，仅检查测量流程，不能作为性能结果。

每档创建独立的临时 profile，生成 832×1216 合成 PNG 和 328×480 缩略图。PNG 使用固定英文词表和可复现的伪随机 Tag，含 NovelAI Comment 元数据，经正式元数据读取器解析。24% 的图片组成每个 20 版本的作品，10% 加入手动收藏集，末尾 5% 位于回收站（收藏集和回收站可重叠）。普通图片使用高压缩的纯色内容；1000 张导入图使用一半随机像素、一半重复像素，PNG 约 1.5 MB，包含不同种子和元数据以避免去重。夹具不依赖用户图片、文件名、Prompt、日常 profile 或 demo profile。

运行三次真实 Electron 进程，每次恢复相同的初始数据库、清除上一轮导入文件和工作台会话/渲染器存储。每档固定一份生产构建副本。这里的“冷启动”指新进程，不主动清空操作系统文件缓存。启动包含数据库打开、窗口就绪、工作台空态显示和命令会话可读取。图库首屏等待视口内所有缩略图解码；搜索 forest、切换合成收藏集等待结果计数更新和列表切换完成；打开作品从图库操作到工作台图片及提示词显示，并检查作品至少有 11 个版本。

窗口尺寸为 1240×760，沿用验收的 offscreen、软件渲染和固定缩放。程序每个 animation frame 滚动两屏，到底再回顶，记录 rAF 间隔大于 50 ms 的数量及最大间隔；这是渲染线程帧间隔，不是显示器呈现延迟。内存来自 `app.getAppMetrics()` 的 working set，分别记录主进程和该窗口的渲染进程，不包含独立 GPU/utility 进程。空闲样本在工作台启动完成后，第二个样本在图库往返滚动后。

结果写入 `.codex-runs/library-benchmark/<规模>-<时间戳>/`：

- `summary.json`：机器配置、夹具占用、三次原始数据和逐指标中位数。
- `run-0.json` 至 `run-2.json`：毫秒、字节、张/秒及长帧数量。
- `main-*.cpuprofile`、`renderer-*.cpuprofile`：主进程和渲染器 CPU 采样，可在开发者工具的 Performance/JavaScript profiler 中读取。
- 超时诊断和截图：沿用验收 harness，失败时不输出成功汇总。

数据库和缩略图大小在导入前测量；`peakProfileBytes` 是导入后 profile 内文件的逻辑字节总数（含输入、构建副本、数据库备份及临时会话），不是磁盘分配单元占用。每轮结束后删除生成的图片、输入图和临时 profile，仅保留测量结果与采样文件。不要把性能差异当作自动化功能验收阈值；功能回归继续使用 `verify:app` 的相关分类。
