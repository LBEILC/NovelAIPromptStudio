# 整体重构计划

> 状态：执行中（准备阶段）
>
> 建立日期：2026-10-11
>
> 基线：v0.10.0（`cce1680`）
>
> 分工：[设计负责人](./roles/design.md) · [工程负责人](./roles/engineering.md) · [任务说明索引](./specs/README.md)

## 1. 为什么做

技术栈的大方向没有选错，不推倒重来。要解决的是两个选得不合适的库，以及代码缺少结构和约束。下面的数字都是 2026-10-11 在基线上量的。

| 问题 | 现状 |
|---|---|
| 界面依赖通用组件库 | `@lobehub/ui`（底层是 antd）约 25 种组件、分布在 10 个文件。构建产物 26MB、315 个文件，其中组件库运行时一个文件 2MB，另有近 300 个用不到的语法高亮文件。`src/styles.css` 里有 24 处 `!important`，并且自己另有一套颜色变量，等于两套主题并存 |
| 数据层每次写入都重写整个库 | `sql.js` 把整个数据库放在内存里，`electron/database.js` 的 `persist()` 每次导出整库并同步写盘，共 22 处调用，发生在主进程。图库通过 IPC 一次全量加载，没有分页 |
| 状态全堆在一个组件 | `src/App.jsx` 1497 行、25 个 `useState`，向图片库页面传 53 个 props，向工作台传 21 个 |
| 没有类型、lint、格式化 | 纯 JS，JSDoc 类型注解为 0。52 个 IPC 通道没有共享的接口定义。JSX 单行最长 504 字符，`styles.css` 有 85 行超过 200 字符 |
| 主进程集中在一个文件 | `electron/main.js` 986 行，52 个 IPC 处理函数 |

数据层的性能影响目前是从代码推断的，还没有实测，阶段 1 的第一件事就是测出基线。

## 2. 已定

以下是 2026-10-11 和用户讨论后确定的。

- **界面全部重新设计**，范围包括产品结构与流程（UX）、视觉识别（VI）、界面（UI）和交互。
- **不用组件库**，自己写组件。方法参照用户的另一个项目 DispatchDock：一份设计令牌、一份可交互的界面稿、一份记录"为什么"的设计文档，组件是一组样式约定加很薄的一层代码。
- **保留 React、Electron、Vite、vitest。** 现有问题不是它们造成的；界面有大量可编辑的状态（输入法、拖拽、框选），不适合去掉框架。
- **迁移到 TypeScript**，和各阶段的重写合并进行，不单独做一次全量迁移。从阶段 0 结束起，新代码一律写 TS。
- **数据层换成原生 SQLite**，具体用哪个库在阶段 1 实测后定。
- **双角色分工**：设计负责人做方向、设计和验收，Codex 做工程。
- `src/lib` 的业务逻辑（约 2900 行，不依赖 React，测试齐全）原样保留，只加类型。
- Tag 的 9 种分类色、"说明文字不小于 11px"、"作品是视觉中心"等原则保留。

## 4. 阶段

阶段 0、1 是纯工程，和阶段 2 的设计互不影响，同时进行。

### 阶段 0：约束与类型地基（工程）

- 加入 TypeScript 配置：严格模式，JS 和 TS 可以并存。加入 `npm run typecheck`。
- 加入格式化工具，把现有代码一次性格式化，单独一个提交，不夹带其他改动。
- 写出共享的类型：图片记录、Tag、Prompt 结构、收藏集、偏好设置，以及 52 个 IPC 通道的请求和返回值。先让 preload 和界面两端用上。
- 如果待定 3 通过：搭好截图脚本，输出现有各页面的深色、浅色截图，作为之后对比的基准。

完成标准：类型检查、测试、构建全部通过；界面和行为没有任何变化。

### 阶段 1：数据层与主进程（工程）

1. **先测基线**：用演示环境造 1000、5000、20000 条图片记录，记录 `persist()` 单次耗时、启动加载耗时、数据库文件大小。数字写进汇报。
2. `src/lib` 迁到 TS。
3. 主进程迁到 TS，加入构建步骤，`main.js` 按领域拆分。
4. 数据库换成原生 SQLite，写入改为增量。**旧版本的数据库文件必须能直接打开**，不需要用户做任何操作【实现时核实】。
5. 用同样的数据量再测一遍，和基线对比。视结果决定图库加载是否需要分页。

完成标准：`electron/database.test.js` 等现有测试全部通过；有旧数据库文件升级的测试；两个平台打包成功。主进程的构建方式和原生模块都是平台敏感的改动，要给 macOS 留交接。

### 阶段 2：设计（设计负责人）

产出 `doc/design.md`、`design/tokens.css`、`design/preview.html`。分三个检查点，每个都要用户确认后再往下走：

1. **结构与流程**：重新梳理工作台、图片库、设置三个页面各自解决什么任务，信息怎么分层，哪些操作该被看见、哪些该收起来。现有的 [体验改进计划](./design-improvement-plan.md) 已经指出的问题（认知密度偏高、高级交互不容易被发现、首次使用引导不足）在这里一并解决。
2. **视觉方向**：2 到 3 个方向的工作台样稿，同时定下配色、字体、图标、应用图标。待定 4、5、6 在这里解决。
3. **组件与关键页面定稿**：全部基础组件的各种状态，工作台和图片库的完整界面稿，深色和浅色、常规和最小窗口尺寸。

### 阶段 3：基础组件层（工程，按定稿实现）

- 新建 `src/ui/`：主题与外观（替换 `LobeProvider`）、基础组件、行为层（菜单、对话框、浮层、提示、通知、下拉选择、滑块、可拖宽面板）。
- 一个组件展示页，列出每个组件的全部状态，用来截图验收。
- 界面文案集中到一个文件，归设计负责人维护。
- 行为层的键盘与焦点要求写进任务说明：方向键、Home、End、Esc、Tab 的行为，关闭后焦点回到触发元素，对话框打开时背景不可操作。

完成标准：组件展示页的截图和界面稿逐个对得上，深色浅色都对得上；这一阶段不改动任何现有页面。

### 阶段 4：逐页迁移（工程，按定稿实现）

顺序：设置页 → 工作台 → 图片库 → 导入弹窗、更新说明、反馈与帮助。

每个页面一次做完四件事：换成新组件、把这一页的状态从 `App.jsx` 搬到独立的状态模块、改成 TSX、去掉这一页对 `@lobehub/ui` 的引用。每页一个任务说明，各自验收：截图对照界面稿，加一份手动验证文档给用户。

拖拽与排序目前有三套机制（dnd-kit、pragmatic-drag-and-drop、motion 的 `Reorder`），迁移工作台时收敛，保留哪一套由工程在任务汇报里给出依据。

### 阶段 5：收尾

- 移除 `@lobehub/ui` 及不再使用的依赖，确认构建产物里不再有组件库运行时和语法高亮文件。
- 归档 `doc/lobe-visual-language.md`、`doc/design-improvement-plan.md`，删除 `.agents/skills/lobe-ui-frontend/`，重写 `.impeccable.md`，更新 `doc/product-boundary.md` 和 `doc/README.md`。
- 更新应用图标、README 截图。
- 两个平台的完整手动验证，然后发版。

## 5. 验收手段

| 对象 | 手段 |
|---|---|
| 类型、逻辑、数据层 | `npm run typecheck`、`npm test`、`npm run build`，以及任务说明里指定的测量数据 |
| 组件与页面外观 | 截图脚本的输出、组件展示页，与 `design/preview.html` 并排对比 |
| 需要动手操作的行为 | 手动验证文档，由用户执行 |
| macOS | `coordination/MACOS.md` 交接 |

## 6. 风险

- **数据安全**：数据库更换涉及用户的真实图库。旧文件兼容是硬性要求，并且要有测试；首次用新数据层打开前自动保留一份旧文件的备份。
- **macOS 验证积压**：`coordination/MACOS.md` 里有三项 8 月留下的待验证项还没做。重构会让其中和旧界面有关的部分作废，但打包和原生模块必须在 macOS 上实际验证，需要安排。
- **范围膨胀**：重构期间不加新功能。重新设计中发现需要增减的功能，在阶段 2 的检查点里和用户确认后写进设计文档。
- **界面迁移期间两套样式并存**：阶段 4 没结束前，旧页面还在用组件库。新旧样式互相影响的问题在阶段 3 的任务说明里要求隔离。

## 7. 不做

- 不更换 React、Electron、Vite。
- 不改 `src/lib` 的业务行为，只加类型。
- 不改变产品边界里"明确不做"的内容。
