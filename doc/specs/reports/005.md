## 1. 完成内容

`electron/database.js` 已直接使用 `node:sqlite` 的 `DatabaseSync` 打开磁盘数据库。保留原有公开函数的参数、返回数据结构及全量图库行为；查询结果仍为普通对象和 Number，包括旧文件中超出 JavaScript 安全整数范围的 INTEGER，沿用旧引擎原来的精度语义。

写入采用 DELETE 回滚日志、`synchronous=EXTRA`，并开启 macOS 可使用的 `fullfsync`。每个现有修改接口都有事务边界；原有内部事务用保存点嵌套，保证返回结果之后才提交整个接口的修改。`persist()` 现在是兼容用空函数；写入已在对应公开方法返回前提交，不导出整库，不触发 checkpoint。

增加 `close()`，可重复调用。正常退出在 `before-quit` 关闭；更新安装在调用 `quitAndInstall()` 前关闭，安装失败而应用继续运行时重新打开连接；初始化失败也关闭连接并回滚。测试先关闭连接，再删除临时目录。

增加 `insertProjects()` 供导入使用：图片解码和异步准备在事务外完成，每 25 张准备好的图片作为一个同步事务，每张图用保存点单独回滚。单张失败不会回滚同批其他成功图片；整批提交失败时只有这一个批次失败，前面已经提交的批次保留。取消时提交已准备的不足 25 张的批次；遇到待提交的同内容图片时先提交当前小批次，再核对重复记录。导入只有在提交成功后才计入 `imported`。

`backfillPromptFingerprints()` 按任务允许的保守分支保留原来的全量计算，原因与证据见第 6 节。它现在也具备事务原子性。

删除两个外部 SQLite 引擎依赖及原型适配器，基准改为直接调用产品实现。Electron 探针也改为运行正式应用入口和正式目录包，以临时 Profile 无窗口验证，不再构建独立研究应用。

## 5. 推断清单

- 选用 DELETE + EXTRA，避免正常退出时额外 checkpoint 的依赖；`fullfsync=ON` 在支持的平台请求更强的同步。
- 将“批量导入不逐张提交”落实为增加批量 API 并让 importer 调用；保留已有 API 不足以知道异步导入的批次边界，因此做了范围有限的调用点接入。
- 批次上限取 25，以限制事务持续时间和准备对象内存；重复项和取消可以形成更小的批次，不跨异步操作持有数据库事务。
- 一次性备份命名为 `studio.pre-node-sqlite.sqlite`，临时复制文件以进程号区分；备份成功前不建立原生连接。
- 初始化时既有 schema 检查和指纹修复放在同一事务中，失败则关闭回滚。
- 对超出安全整数范围的 SQLite INTEGER 沿用旧 API 的 Number 转换，不把返回值升级为 BigInt，也不因新引擎默认读取限制拒绝旧文件。
- 保持旧实现实际的 `foreign_keys=OFF` 状态。启用原生默认级联会扩大永久删除范围，违反保留遗留表的要求；这项决定以旧引擎实测为依据，详情见下文。
- 无窗口验收通过显式 `--database-probe-output=<路径>` 启动正式应用入口，并提前重定向到临时 Profile。普通启动不走探针。

## 6. 实现时核实及任务问题答复

### 单文件、崩溃与持久性

正常提交和关闭后，当前数据库是 `studio.sqlite` 一个文件；两份一次性备份是独立历史副本。没有 WAL/SHM。持久性测试实际读回配置：`journal_mode=delete`、`synchronous=3`、`fullfsync=1`。

SQLite 的 EXTRA 在 DELETE 模式下比 FULL 多同步日志删除所在目录，用于保证提交持久性；macOS 的 fullfsync 请求支持的完整同步。实现采用这些设置，而不是定时缓存或退出时才写文件。依据：[SQLite synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous)、[fullfsync](https://www.sqlite.org/pragma.html#pragma_fullfsync)。这里没有做真实断电测试，也没有将强制结束等同于断电；磁盘和系统仍需遵守同步请求。

强制结束测试在子进程写入返回后直接杀进程；另一个分支用小缓存和大量未提交页，确定产生热回滚日志后杀进程。新版重开时 `integrity_check=ok`，已提交图片/翻译均保留，未提交图片名和 200 条脏数据均回滚，正常关闭后日志消失。事务中途测试使用第二个原生连接确定崩溃位置，因为产品 API 没有可跨异步等待的开放事务接口。热日志恢复机制依据：[SQLite locking and rollback](https://www.sqlite.org/lockingv3.html)。

在移除旧依赖之前，另外用旧提交的真实 `openDatabase()` 对同一崩溃现场的副本做了回读，命令为本地 `.codex-runs/005/old-crash-check.mjs`，结果保存在 `old-crash-results.json`：

| 结束位置 | 磁盘状态 | 新版读取 | 旧版直接读取 | 新版恢复并正常关闭后再用旧版 |
| --- | --- | --- | --- | --- |
| 成功提交后 | 仅主库 | `Committed image`、`已提交` | 相同 | 相同 |
| 未提交事务脏页已落盘 | 主库 + `studio.sqlite-journal` | 恢复为 `Committed image`、保留 `已提交` | 读到 `Uncommitted`，不能正确恢复 | 恢复为 `Committed image`、保留 `已提交` |

**异常退出后不能直接回退旧版。** 旧引擎只读取主文件到内存，不处理磁盘热日志。必须先由新版恢复并正常关闭，再回退或只复制主文件。这个限制已经写入用户验证文档。正常关闭后的合成小库向后读取在上述旧实现检查中通过。旧版仍有原来的 2 GiB 整文件读取限制，不能读取本次约 4.1 GiB 的 20000 张基准库；单文件格式兼容并不会修复旧程序的这个限制。

### 批量导入与 persist

一次 25 张批量写入只发生一次外层提交；测试在中间插入重复主键，证明该图失败、其前后图片成功且重开后仍在。另一个测试注入外层提交错误，证明整个当前批次不生效、前一批次仍在。真实 PNG 导入测试用 30 张图和一张故障图，实际批次为 `[25,5]`，结果 29 成功、1 失败。

`persist()` 是空函数。现有显式依赖点包括主进程 `translation:tags` 的词典/缓存写入、原有数据库方法和测试中的调用。公开 `upsertTagDictionary()`、`upsertDanbooruTagCache()` 现在各自在成功返回前提交，因此调用方不再需要最后一次 `persist()` 才能落盘。没有调用方仍依赖“在内存中修改、persist 时导出整个数据库”的行为。

### 指纹回填

没有采用仅筛空值的优化。现有文件没有记录“该行指纹由哪个算法版本、哪份输入生成”的可靠标记，非空值仍可能过期；`insertProject()` 接受的 Vibe 指纹也不一定与随后从 `extra_json` 提取的实际值相同。任务又禁止新增字段/表，不能以未获证明的假设跳过这些行。

按任务的“做不到完全一致就保持原样”条款，保留旧算法完整遍历。固定旧实现 JSON 已证明正常旧库逐行结果相同；额外测试将四种指纹设为非空过期值，新实现仍恢复到旧实现逐行结果，证明“非空即可跳过”不等价。本次没有声称已经完成选择性回填或解决启动全量计算。

### 遗留表与外键行为核实

提交前用旧提交代码和固定合成夹具核对了永久删除。旧引擎首次 `persist()` 导出后，其连接的 `PRAGMA foreign_keys` 实际为 0；旧代码虽然在初始化 SQL 中写了 ON，但导出重开会重置这项连接配置。如果沿用原生引擎默认 ON，删除一个项目就会级联删除遗留的收藏成员、实验、Vibe、Prompt 版本、分支等记录，违反本任务的数据保留边界。

最终显式保留 OFF，不引入新的外键执行语义。用本地 `.codex-runs/005/cascade-check.mjs` 分别运行旧代码与最终新代码：删除 `image-0` 后，两者均为 projects=2、prompt_tags=3、generation_metadata=6，各遗留表仍为 3 行。新增的固定夹具测试逐行核对所有 12 张遗留表、元数据及 Tags 都未改变；当前收藏集成员仍由已有显式删除语句移除。没有借此次替换清洗历史孤立记录。为复核这项差异，旧引擎仅临时安装在忽略的 `.codex-runs/005/legacy-check/`，没有恢复到产品依赖或仓库代码。

### 退出与更新安装

检查了 `electron/updates.js`、主进程所有退出/安装调用以及当前 electron-updater 的 `BaseUpdater.quitAndInstall()` 实现：原 `updates.js` 仅提供能力判断、版本比较和 Release 查询，实际安装入口在主进程。`autoInstallOnAppQuit=false` 保留；安装任务排程执行时，新增 helper 先同步 `close()` 再调用 `quitAndInstall(false,true)`；普通退出在 `before-quit` 关闭，重复关闭安全。

核实发现 `quitAndInstall()` 安装失败时可能只发 error 而不退出应用。若仅关闭连接就直接调用它，会让失败后的应用继续持有已关闭的数据库。本次通过一次性失败回调重开连接并沿用原有更新错误状态；如果数据库无法重开则走原有数据库错误提示与退出路径。已经开始正常退出时不重新打开。单元测试证明关闭顺序、失败回调去重和关闭失败阻止安装，数据库重开持久性由集成测试覆盖；没有把它们声称为真实安装器交互验证。

不存在依赖最后一次 `persist()` 才落盘的成功写入。异步任务在退出前尚未完成的准备不会计入导入成功，已返回成功的数据库操作已提交。初始化失败会关闭并回滚，测试通过。本次没有真实安装一个更新包，不能声称交互安装流程已人工验证。

## 9. 已知问题

- 大图库启动和全量列表仍同步阻塞主线程，回填仍全量运行；本任务解决增量写入与原子性，没有解决列表规模问题。
- 热回滚日志尚未由新版恢复时，旧版直接打开可能读到未提交内容；应遵守上述恢复顺序。
- 新引擎首次备份增加一个数据库大小的磁盘占用；若历史 pre-phase2 备份也不存在，则这次打开需要两份副本。备份失败不会继续打开。
- 备份的完整副本发布需要数据目录所在文件系统支持普通硬链接；Windows 本机检查通过，macOS 由矩阵测试覆盖。不支持时会安全停止打开，不会无备份继续修改原库。
- 外键级联保持旧实现的关闭状态；未来启用或清理孤立关系需要独立的数据兼容方案。
- Windows 用户数据与交互验证待用户执行；macOS 远端 CI 待设计负责人验收后推送触发。
