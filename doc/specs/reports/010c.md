# 010c 进度事件断言工程汇报

## 1. 完成内容与原因

修正卡片缓存验收对末尾进度的过度要求，以列表请求成功返回作为完成信号。进度事件只负责建立过程的提示；不要求界面收到 `completed === total`，快速完成允许没有事件。类型和产品代码均补充了约定。

另修复一个产品侧问题：原计数来自当前项目与缓存表的联表统计，删除已缓存项目、使已缓存行失效都会让数值下降。现在每次共享建立任务记录已完成张数的高水位，下一次任务重新开始计数；总数仍取实时数据库值。未调整 25 张批次上限、12 ms 预算、让出主线程的方式或持久缓存格式，未增加依赖、界面或文案。

### 本机复现与证据边界

- 原断言在本机自然时序下通过：两套主题 368 条通过，见 `.codex-runs/010c-baseline.log`。
- 验收中将主进程发出的终态事件暂存，在页面收到三个列表回复并取消订阅后才通过真实 `webContents.send` 发送。两个主题均暂存了 2 个终态事件；界面最后收到的是 `307/314`、`312/314`，中间进度存在且所有事件形状正确，两个活动列表均完整一致、回收站列表完整。旧断言的三个条件中，仅第三条为 false。修正后同一受控运行 370 条全部通过，见 `.codex-runs/010c-delayed.log`。
- 快机器跳过全部中间批次的猜测不适用于这组数据：产品每批硬上限为 25 张，300 张新增数据至少需要 12 批。快速条件另外强制每批达到 25 张上限，并断言收到的中间增量符合这个条件。
- 临时恢复旧计数逻辑运行 `vitest run electron/libraryCards.test.js -t "keeps completed monotonic"`，单调性断言确实失败（退出码 1）；恢复修复后通过。见 `.codex-runs/010c-red.log`。这证明计数回退是独立的产品问题，但原 CI 的固定数据流程没有删除/导入，不能将它认作那次 CI 失败的原因。
- 原 CI 没有记录进度实值，因此无法追溯证明其每次失败的具体末尾值。本次复现证明旧断言可因终态投递时序失败，并修复了该不符合约定的依赖；不将受控复现冒充对原 CI 的逐事件观察。

### 末尾事件与列表回复的顺序

当前数据库实现先调用进度回调，再完成列表读取；主进程调用 `webContents.send`，列表则通过 IPC invoke 的回复返回。项目没有“渲染器确认已处理终态事件”的握手，也不将两个通道的界面处理顺序作为契约。列表成功返回即可收起进度，不等待终态事件；迟到事件不得成为完成的前置条件。受控验收覆盖了列表先到、终态后到且监听已解除的情况。

## 5. 推断清单

- 总数可下降且已完成数不可下降，因此删除后 `completed` 可能大于 `total`。采用单次建立高水位，而不钳制到新总数或把进度误作完成标志；类型注释明确这一点。
- 静态验收夹具期间没有导入/删除，因此该场景可以检查每个事件总数等于数据库快照；变化总数另由单元测试覆盖。
- 使用每批 1 张与每批 25 张作为可复现的慢/快条件，而不是依赖机器性能差异；终态延迟注入限于验收作用域。
- 可选失败详情支持渲染器表达式或主进程回调，延迟到失败后求值；旧的两参数调用保持兼容。

## 7. 验收断言与失败说明

- 更新进度断言：存在由多批数据保证的中间事件，字段为 `completed,total`，数值为非负整数，已完成数单调，列表完成。
- 保留建立期间设置导航和其他主进程请求响应、并发列表一致性断言，数量改由数据库读取。
- 新增终态事件晚于回复且取消监听后仍得到完整列表的断言。
- 慢/快模式各新增批次增量断言（1/25 张），确保受控条件实际生效。
- `check(label, expression, failureDetails)` 失败时在检查清单增加 `details`，并在日志输出 `失败说明：<JSON>`；成功时不求值、不写字段、不输出详情。诊断自身报错不会掩盖原断言失败。

单元测试验证的日志示例：

```text
FAIL [启动] progress
Error: 断言值：false
失败说明：[{"completed":25,"total":60}]
context
```

卡片验收传入整个 `window.__cardCacheAcceptance`，实际失败详情包含完整进度列表、pending、设置响应结果和实际列表数量；并发数量失败另附数据库预期值。临时复现日志中的成功时进度输出已经移除，最终实现只在失败时输出这些详情。

自动化没覆盖：本机未运行 macOS 或 Node 22，也未触发远端 CI。现有 CI 矩阵在 Windows/macOS × Node 22/24 上运行单元测试与 `verify:app`，新增普通模式断言自动随之执行；慢/快条件本次在 Windows Node 24 本机运行。没有改动原生窗口拖拽、原生文件对话框或系统外快捷键。
