# 003 工程汇报：数据层基线与选型

## 1. 完成了什么

实现可重复运行的 sql.js / node:sqlite / better-sqlite3 数据层研究脚本、合成旧库兼容性测试、无窗口 Electron 开发与未签名打包探针，扩展 Windows/macOS CI 到 Node 22/24。完整方法、实测表格、候选核实、单文件假设清单及建议见 [数据层研究报告](../../research/data-layer.md)。

建议选择 node:sqlite。5000 张翻译写入中位从 2031.4842 ms 降到 0.7934 ms；better-sqlite3 为 0.6495 ms，两者均可用。全量返回仍达 694.56 MiB，需要下一任务处理按需加载。20000 张原始入口实测因 `readFileSync` 的 2 GiB 限制失败；两个原生候选均在同一约 4.40 GB 文件上完成全部测量。

没有替换产品数据层、没有修改 `electron/database.js` 或其他产品运行时代码、没有读取真实图库。按工程负责人规则提交但不推送。

## 5. 推断清单

1. 任务的 KB 按 KiB 实现，报告表格统一 MiB；文件与 JSON 原始字节保存于测量输出。
2. 元数据分布未给分位数，采用每 100 行一个最大值、其余补齐均值的确定性两点分布。
3. 孤立元数据按 147/159 比例随规模增长；字典与 Danbooru 缓存维持给定 2400/750 行，所有图片共用轮转 Tag 集合。
4. 12 张遗留表使用仓库历史定义，每张放 3 行；未假造未知历史负载以强行凑到 250 KB/图，因此总文件量可能比用户样本偏小。
5. 准备夹具时延迟 persist，真实测量恢复未修改实现；原生候选复用同一 SQL 和返回构造，避免因删减元数据或业务逻辑得到虚假优势。
6. 写入取 7 次总操作中位数/最大值；打开、loadLibrary、100 张导入各运行一次。候选使用 WAL+FULL，不降低耐久性等级换取数字。
7. “导入100张”解释为本任务范围内的数据层导入，不包含图片文件解码或 I/O；JSON 为精确等价字节统计，不是 Electron IPC 实测。
8. 峰值内存取操作进程 maxRSS，隔离准备阶段；每进程设置 12 GiB V8 堆，最终脚本对 20000 及以上 sql.js 夹具准备设 5 分钟上限，其他准备与实际测量设 20 分钟上限。20000 准备失败时保留失败记录，再尝试原生夹具继续验证各入口，避免将准备失败直接当作打开失败。
9. 打包验证使用独立同版本 Electron 探针，产品入口与数据目录都不载入；体积比较是同配置独立包的增量，不能直接替代正式产品最终体积。
10. 根据没有产品行为变化、没有交互验证需求，使用无窗口命令行探针完成本次打包核实，没有创建产品交互手动验证单。

## 6. 【实现时核实】结论与证据

- Electron 开发/打包可用性：两候选均通过。实际 Electron 43.1.1 内置 Node 24.18.0；SQL、WAL、事务、FTS5、预编译写入、在线备份成功。命令与 JSON 摘要见研究报告。
- Vitest 与 Node 22/24：两候选均通过本机实测。Node 22 与本机 24.14.0 的 node:sqlite 打印实验性警告；Electron 24.18.0 没有该警告。
- 原生打包：better-sqlite3 13.0.3 已采用 N-API，本机 `npmRebuild=false` 即可运行；提供 ASAR 外预编译文件。node:sqlite 内置，不引入外部原生模块。
- 体积：未裁剪的 better-sqlite3 探针增加 26.44 MiB 解压体积、8.43 MiB NSIS 体积。完整原始 bytes 见研究报告。
- 稳定性：对应 Node 24.18.0 官方文档为 Stability 1.2（Release candidate），没有将最新 Node 文档的等级套到旧版。
- 同步/异步：两者普通查询/事务接口均同步，backup 为 Promise；不能据此宣称普通查询异步，Worker/进程隔离仍需下个任务评估。
- 旧库直接打开：完整比较 21 张表的全部合成行，包含 12 张遗留表及孤立 generation_metadata；integrity_check=ok，切 WAL 后 sidecar 存在，关闭重开仍保留数据。
- macOS 双架构：包内预编译文件已核对；远端运行结果待验收推送，未把静态文件存在当成运行成功。

## 8. 偏离说明

- 用户样本总量与已知列分布不能唯一确定同一个模拟文件大小，未伪造未知字段负担；报告明确为保守基线。
- 用源码副本的持久化注入准备夹具及适配候选，避免复制并逐渐偏离生产 SQL；生产文件未修改。测量本身的 sql.js 入口没有注入。
- JSON 大小逐项累计，绕过 V8 单字符串上限；仍保持全量 loadLibrary 对象，不把分页优化偷偷计入候选结果。
- 20000 的 sql.js 准备超过时间预算，故用原生连接构造同样的数据文件后继续验证原始入口和两个候选；原始入口实际报大于 2 GiB 的文件读取错误，没有把准备时间限制当成原始入口的容量结论。初次 1000/5000 与最终 20000 分两轮保存，报告合并展示。
- 工程角色禁止推送，因此 macOS CI 实际结果暂不可得；已交付可执行矩阵及证据上传，不能给出“某候选已通过 macOS”的无依据结论。

## 9. 已知问题

- 测量使用合成数据、单次读/导入，不代表所有真实图片元数据、机器、磁盘缓存状态。
- 原型仍全量加载，因此原生 SQLite 不能自动消除巨量 IPC 和 JavaScript 对象内存。
- 研究适配器依赖当前 database.js 的函数形状；将来产品结构变化应同步更新研究脚本并通过等价测试，不能作为产品持久化实现使用。
- 本机 Node 22/24.14 的 node:sqlite 实验性警告是实际运行时状态，不影响本次测试通过。
- 远端 macOS CI 尚待验收推送后执行；没有冒充该平台的实测结论。
