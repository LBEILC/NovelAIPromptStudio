# 010a 图库列表生成耗时工程汇报

## 1. 完成内容

在 `rebuild/ui-1.0` 优化 `loadLibraryCards()`：增加一张可删除重建的派生缓存表，缓存卡片投影；用持久脏标记只重建受影响的图片；同一次运行复用已解码的结果。列表筛选与排序在缓存表的窄索引上进行，不再每次读取、排序原表里的长指纹，也不再扫描全部 Tag 和完整元数据。

所有测试与测量使用临时目录和本任务生成的合成样本，没有打开日常图库。只管理本任务启动的子进程；提交留在当前分支，不推送。

## 5. 推断清单

- 派生表保存完整卡片投影及筛选、排序需要的标量，包含名称、路径和状态。只缓存 Tag/相似度不足以达标：原表长指纹的读取和排序仍占据热路径。
- 复用 010 的九个跟踪触发器，同时写入独立的 `library_cards_dirty:<id>` 标记。两个消费者独立消费脏标记，避免列表先消费后导致启动指纹补算漏掉变更。新增一个只跟踪展示字段的触发器，不把改名和状态变化当成指纹变更。
- 缓存失效采用整个词典的语义签名；忽略不参与卡片派生的 `updated_at`、`display_tag`，避免导入相同知识时全库重建。真正的译文、分类及来源等输入变化保守地使全部派生卡片失效。
- 首次调用列表时建立所有图片（含回收站）的投影；以后按请求视图返回。持久缓存是按需建立的，不在尚未使用新列表接口时主动增加启动工作。
- 以原始 `projects.rowid` 保存同一 `created_at` 下的顺序；缓存表的插入顺序不参与结果排序。
- 封面仍读取当前 `prompt_group_covers`。缓存内部用精确指纹的 SHA-256 对应封面，避免重复存储长的精确分组指纹；对外的原指纹和分组键不变。
- 公共卡片中的重复数据采用共享对象，不增加新字段或改成短分组键。IPC 耗时包含生产 preload 的 `invoke` 与返回克隆，不包含图库布局和绘制。
- 基准中的单图 Tag 修改使用独立 SQLite 连接修改该图的权重，以覆盖不知道缓存约定的写入方；改名、回收站和批量导入走现有产品 API。写入本身与写入后的列表分别计时。

### 原来的约 6.5 秒花在哪里

先对修改前的 010 实现做同分布 5000 张测量，再选择缓存方案。010 报告为 6481.07 ms；本轮带分段计时的基线为 **6281.04 ms**。

| 工作 | 本轮 ms | 口径 |

| 逐图查询并读取元数据 | 1588.64 | 5000 次查询，包含 `extra_json`、结构及其他元数据的读取，不能将同一次 SQL 的 I/O 再拆成独立的字段耗时 |
| 解析 `extra_json` | 195.16 | 原本包含在相似度派生调用内，此表单独列出 |
| 丰富 Tag | 365.78 | 词典、规则分类和译文 |
| 相似度派生，扣除上述 `extra_json` 解析 | 1007.48 | 原始包含解析的调用耗时为 1202.65 ms |

最终复测复用由既有 `seed()` 生成的相同合成快照。`--fixtures-root` 要求匹配的合成数据清单及图片数，只读源文件，在新的临时副本中删除派生表后测量重建。所有最终数字均为单轮墙钟观测，热读取取该轮最大值，不是多轮分位数或磁盘冷缓存统计。本机仍有用户的其他项目任务运行，没有为测量结束其他进程。

环境为 Windows x64、AMD Ryzen 9 9955HX、Node 24.14.0、Electron 43.1.1，约 31.18 GiB 内存。样本保持既有每图 59 个 Tag、`extra_json` 平均 62 KiB/峰值 271 KiB、结构平均 21 KiB/峰值 41 KiB，并保留孤立元数据和遗留表。没有使用真实图库，也没有压缩或删减样本内容。

重开测量关闭并重新打开数据库，清除连接内缓存；热读取测三次。真正的 Electron 首次请求在新进程中进行，持久表由另一个进程事先准备，不在同一 Electron 进程预热列表函数。渲染器计时从调用 `window.studio.loadLibraryCards()` 前开始，到收到完整数组为止，断言数量和精简结构之后才进行下一轮；没有把“只查数据库”的时间当成 IPC 时间。

首建仍为同步事务：接口在所有卡片建立成功后返回完整结果，失败时回滚缓存和脏标记，不返回半份列表。**可以分批**：保留主线程数据库，在批次间让出事件循环，并让同时到达的列表请求等待同一个建立任务，完成后一次返回完整结果；需要同时设计期间写入的失效处理。当前没有实施这一额外异步流程，也没有添加进度提示。

### 缓存内容与词典正确性

只新增 `library_card_cache` 一张表，以及这张表自己的排序覆盖索引。表中保存图片 id、原始行序、创建时间、收藏/回收站状态、编码后的完整卡片投影和内部封面查找摘要。投影包括尺寸、模型、原有指纹、筛选 Tag、搜索原文和相似度键值数组；不保存完整 `extra_json`、完整结构、详情或图片字节。内存的共享对象只是 JSON 缓存解码后的表示，不改变公共字段类型。

`app_meta.library_cards_version` 保存算法版本和词典语义签名。每次读取在同一个 SQLite 事务里查询并检查 `tag`、`translation`、`category`、`has_translation`、`has_classification`、`translation_source`、`category_source`。这些字段或行的增删发生变化，会整体重建派生缓存；旧版直接写词典也会被发现。缓存中虽然包含译文、分类和加权结果，但在返回之前核验签名，不会把旧权重继续返回。时间戳或展示名变动不影响计算，测试断言它们不会触发元数据重读。

删除整张表后会自动重建；同进程删表用 SQLite schema 版本检测并清除内存。测试比较重建前后的全部卡片及所有原始业务表行。缓存写入、脏标记消费在一个事务内，失败时清空进程内缓存并保留可重试的脏标记。

### 退回旧版本再升级

010 原有触发器继续保留；更新其定义时只补充卡片脏标记。卡片标记和业务写入同事务提交/回滚，触发器不引用派生表，所以即使删除了缓存表，旧版仍能写入。新版本启动在清除原指纹脏标记前先使相应卡片失效；还兼容只有 010 原始指纹标记、没有卡片标记的写入。缺失跟踪或强制全量补算会保守地清掉派生结果。

实际旧版 `sql.js` 验证执行“新版建立缓存 → 旧版导入、改名、移入回收站、修改词典 → 新版重开”。九个原跟踪触发器保留，旧版导入留下卡片标记，缓存表能被旧引擎读写和导出；新版所有视图、筛选及每对相似度与完整接口一致，再强制全量补算后结果不变。工具通过参数读取本机保存的旧实现和隔离安装，不把旧引擎加回产品依赖。

## 7. 新增验收断言与自动化没覆盖

- 同进程删表以及关闭数据库、删表后重开，卡片完全相同，原始业务表逐行不变。
- 词典译文、分类权重和删除立即生效；旧写入修改词典后重开仍正确；只改时间戳和展示名不重算。
- 冷/热命中不读取完整元数据或 Tag；导入、连续修改同一图、改名和回收站只更新受影响 id；回滚写入不使无关卡片失效。
- 缓存已建立后，旧写入的修改、删除和 010 原始触发器标记均能正确失效；与全量重算一致。
- 热缓存下读取和切换精确分组封面仍正确；原来的分组、成员、排序、筛选、收藏、相似度和补算测试全部保留。
- 缓存写入失败时，脏标记与旧缓存事务回滚；重试没有残留的错误内存结果。
- 正式应用新增重复列表 IPC 逐项一致和改名后立即可见两条断言，随主题与重启阶段执行。
- 基准在 5000 张时对冷/热、单图三种修改、导入后和真实 IPC 分别输出可读的布尔阈值检查，未达标会失败；20000 张只记录测量值。

自动化没覆盖：本机未运行 macOS，等待设计负责人推送后由既有 CI 覆盖；没有真实断电及真实用户图库测量；独立 IPC 大图库基准不覆盖页面布局、绘制、启动内容回填或操作系统磁盘冷缓存。任务未改动原生窗口、文件对话框或系统快捷键，没有新增手动检查清单或 macOS 交接。

## 9. 已知问题

- 首次建立、词典语义变化及派生算法升级仍会同步重建全部卡片，有一次性主线程阻塞；分批建议已交由设计决定。
- 当前旧图库界面仍调用原 `loadLibrary()`，可见的加载收益需要 012 接入新列表接口；本任务遵守“不改界面”的范围。
- 共享对象的传输收益取决于数据重复度。基准对应约定的合成分布，不能视为所有真实图库的硬实时保证；大型图库仍保存原来的完整分组指纹。
- 20000 张冷读取仍有约 1.68 秒的真实主线程阻塞和 2.26 秒端到端 IPC；任务对这一档没有硬指标。每次读取的词典语义签名也仍按词典大小线性扫描。
- 将来修改卡片派生规则或缓存编码，必须提升缓存算法版本。缓存、日志、旧引擎安装和测量证据均不进入 Git。
