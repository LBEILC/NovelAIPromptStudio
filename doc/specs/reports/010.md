# 010 图库数据接口工程汇报

## 1. 完成内容

在 `rebuild/ui-1.0` 增加 `loadLibraryCards(view)` 和 `loadLibraryDetail(id)` 两个 IPC 接口。卡片包含每张图的 `metadata.width`、`metadata.height`，供 012 的等高排列使用；尺寸未知时保留数据库语义并返回 0，012 再按其说明采用 832 × 1216 的布局后备比例。详情复用 `loadProject()`，与旧 `loadLibrary()` 中同一张图片逐项一致，找不到 id 时返回 `null`。旧列表接口和界面调用均保留。

主进程用当前词典丰富 Tag，再生成筛选用 Tag 和 Base Prompt 相似度的有序键值数组。前端把数组恢复成 Map，直接使用原来的加权相似度算法。完整 Prompt 指纹已经含有基础部分：主进程逐行验证 `JSON.stringify(JSON.parse(prompt_fingerprint).base)` 与存储的基础指纹完全相等时，将卡片的 `base_prompt_fingerprint` 设为 `null`，由基础分组路径无损恢复该字符串；不相等、旧指纹不是 JSON 或基础指纹为空时都保留原值。这个明确的卡片协议减少重复传输，不修改数据库指纹或分组键。新旧路径的分组键、指纹、成员顺序、封面、数量、排序和两两相似度均逐项比较通过。卡片另带原始正面、负面和角色 Prompt 文本，供段落搜索使用；旧界面仍使用旧接口，其搜索行为不变。

启动补算改为现有 `app_meta` 内的算法版本和逐图片脏标记。新增九个持久 SQLite 触发器，不新增表或列。旧版写入同一数据库时触发器仍执行；触发器标记与写入一起提交或回滚。无变更重开不读取任何图片的完整元数据；首次安装跟踪、算法版本变化或跟踪触发器缺失时全量补算。公开的 `backfillPromptFingerprints()` 默认仍可强制全量计算，作为维护入口和等价性验证基线。

没有新增依赖，没有更改图片文件、界面、设计令牌或数据库线程归属。测试、基准和应用验收全部使用临时目录/合成数据，未打开日常图库，也未结束其他项目的进程。

## 5. 推断清单

- 新接口命名为 `loadLibraryCards` / `loadLibraryDetail`，视图参数沿用旧接口；详情不存在时沿用数据库 `loadProject()` 的 `null` 语义。
- 图片宽高保留在 `metadata` 子对象，与现有图库读取路径一致；不把 012 的布局后备值写回数据库或卡片。
- `filter_tags` 汇总所有范围，`search_prompts` 覆盖正面、负面和角色原文；重复原文仅保留一次，不影响“包含文本”的匹配结果。
- 相似度数据以有序键值数组传输，避免依赖 JSON 对 Map 的支持，跨 Electron IPC/Worker 结构化克隆后结果仍一致。
- 完整指纹保留原字符串，基础指纹采用经逐行相等验证的 `null` 复用协议，保证分组键、封面参数和空指纹行为完全一致；没有改成短哈希或更换分组标识。
- 用持久 SQLite 触发器捕获旧版写入。触发器属于现有数据库的 schema 对象，但没有新增表或列；状态都在任务指定的 `app_meta` 中。
- 改名、收藏、移入/恢复回收站和路径变动不会改变指纹输入，因此不标脏；元数据和 Tag 写入按所属图片标脏。Tag 字典只改变译文、分类及其来源，原指纹的语义字段不包含这些注解，因此不使指纹失效；卡片每次读取最新词典，分类权重的相似度不会缓存过期。
- 跟踪触发器缺失时无法证明期间没有旧写入，按全量补算处理；算法版本升级同样全量处理。启动事务成功前不清理标记。
- 基准沿用 005 的产品数据库 API 和合成分布，不新增依赖或迁移到 Worker。

## 6. 实现时核实、测量及问题答复

### 补算正确性

算法版本键为 `prompt_fingerprints_version`，当前值 `1`；每张图的标记为 `prompt_fingerprints_dirty:<完整 id>`。对 `projects`、`prompt_tags`、`generation_metadata` 的 INSERT/UPDATE/DELETE 建立持久触发器；项目 UPDATE 只跟踪 id 和四种指纹字段，Tag/元数据 UPDATE 同时标记 OLD/NEW 所属 id，避免迁移归属后漏掉原项目。删除/孤立元数据的标记最终通过项目表筛选，不重建已删除图片。

首次跟踪、版本不一致、触发器缺失时使用原算法全量处理；其他启动只查询标脏项目。补算、旧封面修复、版本写入和脏标记消费处于同一个初始化事务。主动调用无参数 `backfillPromptFingerprints()` 仍强制全量。

最容易出错的是“旧版写入了非空但过期的指纹”，以及只观察 `updated_at` 导致漏掉元数据/Tag 单独更新。本实现不依赖时间戳或指纹空值：测试直接使用不知道新标记约定的 SQLite 写入语句导入、改 Tag、改元数据和写非空旧指纹，重新打开时仅相关 id 被 hydrate；随后强制全量重算的修改数为 0，全部记录逐项相同。测试也断言无变更和仅改名重开 hydrate 次数为 0，新增一张图仅处理其 id，算法版本变化和丢失触发器才全量处理。

额外在本机复用了 005 保存的真实旧版 `sql.js` 实现与已安装的隔离旧引擎，对新建临时库执行“新版建立跟踪 → 旧版打开、导入、改名 → 新版打开”。命令 `node .codex-runs/010-old-writer.mjs` 通过：九个触发器在旧版导出后仍保留，新导入留下 `prompt_fingerprints_dirty:image-1`，两张图和旧版改名均保留，新版结果与强制全量重算完全一致。证据为 `.codex-runs/010-old-writer.json`；临时脚本与旧引擎不进入产品依赖或提交。仓库测试不依赖这份本机安装，CI 通过固定旧文件和模拟旧写入测试覆盖同一约定。

启动补算失败测试在指纹 UPDATE 处注入 SQLite ABORT：打开失败后旧指纹和脏标记都仍在，删除故障触发器后重开成功，并再次与全量结果一致。既有旧数据库逐表比较继续保留所有业务数据、孤立记录和遗留表；只允许任务要求的新版本键及脏标记生命周期。

### 数据库操作移出主线程的评估

可把数据库连接及同步查询放入专属 Worker，由主进程异步请求，并让同一 Worker 串行处理所有数据库操作。这样能避免解析旧结构、丰富 Tag、计算相似度时直接阻塞 Electron 主线程，但不会减少读取/解析的总量，也不会缩小卡片中长字符串指纹的体积；消息传输本身仍有复制、序列化和内存成本。

工程成本包括：所有同步数据库调用者改为异步、导入批次的事务边界、启动/退出/更新时的连接生命周期、存储目录切换和取消、Worker 崩溃后的错误传播与重开，以及跨平台回归。不能把同一个 SQLite 连接交给任意多个线程共享。建议作为后续独立任务实施，本次未移动数据库操作。

## 7. 新增验收断言及自动化没覆盖

## 8. 偏离说明

无功能范围偏离，两个量化目标均达到。实现中无界面改动、无新表/字段、无数据库线程迁移。通过额外触发器保存旧版写入的可靠失效信息，这是在任务限制内实现选择性补算的工程方案。卡片基础指纹使用明确的无损复用协议，完整记录和数据库中的原值保持不变；012 应继续使用已有分组函数消费卡片，不把 `null` 误当作空指纹。最长阻塞指标采用同步 API 分段计时，未扩展成真实 Electron 大图库压力测试，口径与限制已在上文说明。

## 9. 已知问题

- 卡片读取仍同步处理所有匹配图片，旧结构修复的负面 Prompt 可能来自 `extra_json`，因此列表会在主进程逐图读取和解析它，但不把它或完整结构返回前端；大型图库仍有可见的主线程阻塞风险。
- 首次升级/算法版本升级仍需全量补算；首次备份成本也保持，第二次无变更打开的速度不能代表首次打开。
- 原有 `loadLibrary` 的大返回量暂时保留，当前旧图库界面仍使用它；用户可见的图库加载收益要等 012 接入新接口。
- 修改未来指纹语义时必须提升版本键；若未来旧版会主动删除跟踪或清空 `app_meta`，重新打开会安全全量补算。
- 旧引擎的异常退出/热日志兼容边界与 005 相同，本次没有改变。
