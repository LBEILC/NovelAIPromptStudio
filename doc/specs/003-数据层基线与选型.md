# 003 数据层：性能基线与原生 SQLite 选型

> 阶段：[重构计划](../rebuild-plan.md) 阶段 1 的第一步
>
> 执行者：工程负责人

## 目标

用实测数据回答三个问题，为下一步更换数据层做决定：

1. 现在的数据层在不同图库规模下到底有多慢、多占内存？
2. 换成原生 SQLite，用 Node 内置的 `node:sqlite` 还是 `better-sqlite3`？
3. 现有用户的数据库文件，新的数据层能不能直接打开？

**这个任务不更换数据层，不改变应用的任何行为。** 产出是测量脚本、兼容性测试和一份有数据的报告。

## 背景事实

现在用的是 `sql.js`：整个数据库在内存里，`electron/database.js` 的 `persist()` 每次导出整库并同步写盘，发生在主进程。

设计负责人只读查看了一个真实图库，供你构造测试数据时参照。**你不要去读用户的真实数据库。**

| 项目 | 数值 |
|---|---|
| 图片数 | 159 |
| 数据库文件 | 约 40 MB |
| 每张图平均 Tag 数 | 约 59 |
| `generation_metadata.extra_json` | 平均约 62 KB，最大约 271 KB，合计约 18 MB |
| `generation_metadata.prompt_structure_json` | 平均约 21 KB，最大约 41 KB |
| `tag_dictionary` | 约 2400 行 |
| `danbooru_tag_cache` | 约 750 行 |
| 没有对应图片的 `generation_metadata` 行 | 147 行（共 306 行） |
| 旧版本遗留、当前代码不再使用的表 | `vibe_transfers`、`vibe_library`、`vibe_encoding_index`、`prompt_versions`、`branch_recipes`、`branch_results`、`series`、`series_members`、`experiments`、`experiment_members`、`collections`、`collection_members`，其中部分有数据 |

也就是说，每张图在数据库里约占 250 KB，数据库大小基本随图片数线性增长。

## 范围

### 1. 基线测量

新增一个可以用一条命令运行的测量脚本（放在 `scripts/` 下，并加一个 npm 脚本），在临时目录里用**现有的** `electron/database.js` 建库并写入模拟数据。

- 规模：1000、5000 张图片。再尝试 20000 张；如果在这个规模下无法完成（内存不足、超过 WASM 上限、耗时过长），记录失败的位置和原因，这本身就是结论。
- 模拟数据的大小分布按上表构造，尤其是 `extra_json` 和 `prompt_structure_json` 的体积，不要用几十字节的占位内容。
- 每个规模测量并记录：
  - 打开已有数据库到可用的耗时。
  - `loadLibrary` 的耗时，以及返回数据序列化后的大小（它要通过 IPC 整个传给界面）。
  - 修改一个 Tag 的翻译后 `persist()` 的耗时。取多次的中位数和最大值。
  - 导入 100 张图片的总耗时。
  - 数据库文件大小。
  - 进程的内存占用峰值。
- 输出一张 Markdown 表格。

### 2. 两个候选的原型

为 `node:sqlite` 和 `better-sqlite3` 各写一个**只覆盖上面这几项操作**的最小原型（不是完整的数据层），在同样的规模下跑同样的测量，并使用增量写入和 WAL。原型代码放在 `scripts/` 下，不被应用引用。

对每个候选逐项核实，结论和证据写进报告【实现时核实】：

- 在本项目的 Electron 43 主进程里能不能用：开发模式下能否加载；打包后能否加载（至少在 Windows 上实际打一个不签名的目录包验证）。
- 在 vitest 里能不能用。注意 CI 用的是 Node 22，本机是 Node 24，两者都要考虑。
- 对打包的影响：是否需要针对 Electron 重新编译、是否需要从 asar 里解包、对 `release.yml` 里 macOS 同时打 x64 和 arm64 有什么影响、安装包体积变化。
- 是否支持 WAL、事务、全文检索（FTS5）、预编译语句、在线备份。
- 是否有同步和异步两种接口，各自是否会阻塞主进程。
- 稳定性：`node:sqlite` 在 Electron 43 内置的 Node 版本里处于什么稳定级别，是否会打印实验性警告。

### 3. 旧文件兼容

写成 vitest 测试，随 `npm test` 运行：

- 用现有代码生成一个数据库文件，其中包含当前使用的全部表，**以及上表列出的遗留表**（各放几行数据）和没有对应图片的 `generation_metadata` 行。
- 用每个候选直接打开这个文件：`PRAGMA integrity_check` 通过，每张表的行数和抽样内容一致，遗留表和孤立行都还在。
- 切换到 WAL 之后会多出 `-wal` 和 `-shm` 两个文件。找出代码里所有"假设数据库是单个文件"的地方并列进报告：备份、资源库迁移、演示环境、测试等。只列出，不修改。

### 4. CI

让兼容性测试在 CI 的 Windows 和 macOS 上都运行，用来确认原生模块能在 macOS 上加载。不能破坏现有的 CI 步骤。

## 不做

- 不修改 `electron/database.js` 以及任何被应用引用的代码的行为。
- 不把候选库接入应用。可以为原型和测试添加开发依赖；如果最后不采用，下一个任务会移除。
- 不读取、不复制用户的真实数据库。所有测试数据都在临时目录里生成。
- 不设计新的表结构，不做数据迁移方案。

## 验收标准

1. 一条命令能跑完测量并输出表格；报告里有 1000 和 5000 两个规模的完整数字，20000 要么有数字、要么有明确的失败记录。
2. 兼容性测试在本机通过。
3. `npm run format:check`、`npm run typecheck`、`npm test`、`npm run build` 全部通过，测试数量不少于现在的 288 个。
4. 应用的行为没有变化：`electron/database.js` 没有被修改。
5. 报告里的每个结论都有对应的命令和输出摘要。

## 汇报要回答的问题

1. 现有数据层在多大规模下开始不可用？表现是什么？
2. 两个候选在 5000 张规模下，单次修改 Tag 的写入耗时分别是多少？相对现在快多少倍？
3. 哪个候选在 macOS 的 CI 上能直接通过？另一个卡在哪里？
4. 采用你推荐的候选后，打包流程需要改哪些地方？
5. `loadLibrary` 一次全量加载在 5000 张规模下要传多大的数据？是否需要改成分页？
