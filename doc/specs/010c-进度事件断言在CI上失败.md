# 010c "进度事件"断言在 CI 上失败

> 阶段：[重构计划](../rebuild-plan.md) 阶段 4
>
> 执行者：工程负责人
>
> 分支：`rebuild/ui-1.0`
>
> 依据：CI 运行（提交 `e97744f`）。macOS + Node 22 通过；macOS + Node 24、Windows + Node 22、Windows + Node 24 失败。

## 现象

三个失败的组合都只失败这一条（Windows 上浅色和深色各一次，macOS + Node 24 上一次）：

```
FAIL [卡片缓存] 只读进度事件包含已完成张数和总数，最终覆盖全部图片
```

同一段流程里的另外两条（建立期间仍能切换设置页面、并发请求等待同一建立过程）都通过。本机 5 次都通过。

## 设计负责人看到的线索（不一定是全部原因，要你核实）

`electron/acceptance/cardCache.js` 里这条断言同时要求三件事：

1. 至少有一个中间进度（已完成大于 0 且小于总数）；
2. 每个事件的形状正确；
3. 最后一个事件是 `314 / 314`。

而页面里的脚本在三个列表请求返回后，立刻在 `finally` 里取消了进度监听。如果"已完成 = 总数"的那个事件是在列表结果之后才到达界面的，它就收不到，第 3 条失败。机器快的时候 300 张可能一两批就建完，第 1 条也可能失败。

## 范围

### 1. 查清原因

在本机复现（可以用放慢或加快建立过程、调整批次大小等办法模拟 CI 的时序），确认是哪一条或哪几条不成立。写进汇报。

### 2. 把约定定下来并测试

012 的界面要靠这个事件显示"正在整理图片库 1,200 / 5,000"。约定如下，产品代码和类型里的注释都按这个来：

- **列表请求返回，就是建立完成的信号。** 界面在列表结果到达时收起进度，不依赖"已完成 = 总数"的事件。
- 进度事件里的"已完成"只增不减，"总数"在一次建立过程中可以因为期间的导入或删除而变化。
- 建立过程很快（没有产生任何中间批次）时，可以一个进度事件都不发。
- 如果产品现在的行为和这三条不一致，改产品；如果只是断言写得比约定更严，改断言。

断言照约定改：不再要求最后一个事件等于某个固定的数；中间进度是否出现，用足够大的数据或可控的批次来保证，不靠运气。断言里不要写死 `314` 这样依赖演示数据张数的数字，从数据库里取实际数量。

### 3. 失败时要看得到实际值

这次失败只留下"断言值：false"，从 CI 的日志里看不出当时收到了哪些进度。给验收脚本的 `check` 加一个可选的"失败时附带的说明"：断言失败时把相关的实际值（这里是进度事件的列表）写进检查清单和日志，通过时不写。先用在这一条上；009a 改过的那 38 处里，失败时值得看实际值的顺手加上，不强求全部。

### 4. 证明稳定

改完后本机连续跑 5 次 `npm run verify:app`，另外在放慢和加快建立过程两种条件下各跑通一次，写进汇报。

## 不做

- 不改界面。
- 不改缓存的建立方式和性能。

## 验收标准

1. `npm run format:check`、`npm run typecheck`、`npm test`、`npm run build`、`npm run verify:app` 全部通过。
2. 约定在 `src/shared/ipc.ts` 的类型注释里写明，并有单元测试覆盖三条约定。
3. `verify:app` 连续 5 次 0 失败。

远端 CI 由设计负责人推送后确认。
