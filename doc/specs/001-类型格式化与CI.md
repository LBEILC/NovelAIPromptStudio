# 001 类型检查、格式化与 CI

> 阶段：[重构计划](../rebuild-plan.md) 阶段 0
>
> 执行者：工程负责人

## 目标

给项目装上三道自动检查：类型检查、格式检查、两个平台上的 CI。这是后面所有重构的安全网。

**这个任务做完后，应用的界面和行为不能有任何变化。**

## 范围

### 1. TypeScript

- 加入 `tsconfig.json`：
  - `strict: true`，不关闭它下面的任何子项。
  - `allowJs: true`、`checkJs: false`：现有的 JS 文件不检查，但 TS 文件可以引用它们。
  - `noEmit: true`。只做检查，不产出文件；界面仍由 Vite 构建。
  - 覆盖 `src/` 和 `electron/`，排除 `dist/`、`release/`、`node_modules/`、`third_party/`。
  - 其余选项按 Vite + React 19 + Electron 的常规写法配置，选了什么列进推断清单。
- 加入 `npm run typecheck`。
- **不把任何现有的 `.js` / `.jsx` / `.cjs` 改成 TS。** 主进程现在由 Electron 直接运行源文件，并且直接引用 `src/lib` 里的文件，没有构建步骤，改后缀会让应用无法启动。迁移在后续任务里做。

### 2. 共享类型

新建 `src/shared/`，只放类型，不放运行时代码：

- `src/shared/types.ts`：领域模型。至少包括图片记录（图库里的一条）、Tag、Prompt 结构与作用域、生成参数、Vibe、收藏集、Tag 词典条目、偏好设置与外观设置、更新状态、导入进度。字段以实际代码为准，来源是 `electron/database.js` 的建表语句和查询结果的组装代码、`electron/` 下各模块的返回值、`src/lib` 里对这些对象的使用方式。
- `src/shared/ipc.ts`：导出 `StudioApi` 接口，逐个描述 `electron/preload.cjs` 暴露在 `window.studio` 上的每一个方法：参数类型和返回类型。返回类型要追到 `electron/main.js` 里对应的处理函数，写出真实的形状，不要用 `any`、`unknown` 或 `Record<string, unknown>` 代替。确实无法从代码确定的字段，写出能确定的部分，并在推断清单里逐条列出。
- `src/shared/global.d.ts`：声明 `window.studio` 的类型为 `StudioApi`（它在非桌面环境下可能不存在）。
- 让 `electron/preload.cjs` 受类型约束：文件顶部加 `// @ts-check`，暴露给界面的对象用 JSDoc 标注为 `StudioApi`。效果是以后在 preload 里增加、删除或改名一个方法而没有同步改 `StudioApi`，`npm run typecheck` 会报错。除了这两处标注，preload 的运行时代码不改。

### 3. 格式化

- 加入 Prettier，配置为：`singleQuote: true`、`semi: true`、`printWidth: 100`、`trailingComma: "all"`、`endOfLine: "auto"`，其余用默认值。`endOfLine` 必须是 `auto`：本仓库在 Windows 上检出为 CRLF，CI 的 Windows 机器也是。
- 格式化范围只包括 `src/`、`electron/`、`scripts/` 下的 `.js`、`.jsx`、`.ts`、`.tsx`、`.cjs`、`.mjs`，以及根目录的 `vite.config.js`。
- 用 `.prettierignore` 明确排除：所有 CSS（`src/styles.css` 之后会整体重写，而且 `src/styles.test.js` 直接匹配它的文本）、所有 Markdown 和 JSON、`electron/data/`、`third_party/`、`dist/`、`release/`、`demo/`、`doc/`、`build/`、`.agents/`。
- 加入 `npm run format`（写入）和 `npm run format:check`（只检查）。
- 提交要分开：
  1. 一个提交只加工具和配置。
  2. 一个提交**只包含** `npm run format` 的输出，不夹带任何手写改动。
  3. 之后加一个 `.git-blame-ignore-revs`，写入第 2 个提交的哈希。
- 如果格式化后有测试失败，原因只可能是测试依赖了源码的文本排版。这时修改测试的匹配方式，让它不依赖排版，不改变它要保证的事情；改了哪些测试写进汇报。不允许为了让测试通过而回退或手工调整格式化结果。
- 【实现时核实】格式化没有改变界面代码的行为：在第 2 个提交的前后各跑一次 `npm run build`，比较 `dist/` 里由项目自己的代码生成的 JS 产物（主入口和各页面的 chunk，忽略文件名里的哈希）。内容应当完全一致。不一致时找出原因并写进汇报。

### 4. GitHub CI

新建 `.github/workflows/ci.yml`：

- 触发：推送到 `main`、任何 pull request、手动触发。同一分支上有新的运行时取消旧的。
- 两个平台各跑一遍：`windows-latest` 和 `macos-latest`。一个平台失败不取消另一个。
- Node 版本、`actions/checkout`、`actions/setup-node` 的版本与现有的 `.github/workflows/release.yml` 保持一致，开启 npm 缓存。
- 步骤依次为：`npm ci`、`npm run format:check`、`npm run typecheck`、`npm test`、`npm run build`。
- 权限只给 `contents: read`。
- `release.yml` 里在打包前加上 `npm run typecheck`，其余不动。

CI 只有推送后才会真正运行，推送由设计负责人在验收后做。你要保证的是：工作流文件语法正确，并且其中每一条命令在本机都跑通过。

## 不做

- 不改任何现有文件的后缀，不给现有 JS 文件补 JSDoc 类型（preload 的那两处标注除外）。
- 不加 ESLint 或其他 lint 工具。
- 不改 `src/styles.css`、`src/fonts.css`。
- 不改任何运行时行为，不重构，不顺手修 bug。看到的问题写进汇报的"已知问题"。
- 不升级现有依赖。新增的依赖只有 TypeScript、Prettier 和必要的类型包（`@types/*`），版本写精确版本号，和 `package.json` 现有写法一致。

## 验收标准

1. `npm ci`、`npm run format:check`、`npm run typecheck`、`npm test`、`npm run build` 全部通过。测试数量不少于改动前（改动前是 51 个测试文件）。
2. 故意在 `electron/preload.cjs` 里把一个方法改名，`npm run typecheck` 报错；改回后通过。把报错信息贴进汇报，然后确认改动已经还原。
3. `StudioApi` 的方法数量与 preload 实际暴露的方法数量一致，汇报里写出这个数字。
4. 格式化提交只包含格式化工具的输出。
5. 构建产物对比的结论（见上面的【实现时核实】）。
6. `git status` 干净，没有遗留的临时文件。

## 汇报要回答的问题

按 `doc/roles/engineering.md` 的汇报格式写，另外回答：

1. `StudioApi` 一共多少个方法？哪些方法的参数或返回值是靠推断写出来的，各自不确定在哪里？
2. 写类型的过程中，有没有发现主进程返回的形状和界面使用的方式对不上的地方？逐条列出文件和行号。这类问题只列出，不修。
3. 现有代码里有没有同一种对象在不同地方字段名不一致的情况（比如同一个字段有的地方用下划线、有的地方用驼峰）？
4. 格式化一共改了多少个文件、多少行？
5. `tsconfig.json` 里除了本说明指定的选项，还加了哪些，各自的理由。
