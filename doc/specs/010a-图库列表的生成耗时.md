# 010a 图库列表的生成耗时

> 阶段：[重构计划](../rebuild-plan.md) 阶段 4，012（图片库界面）的前置
>
> 执行者：工程负责人
>
> 分支：`rebuild/ui-1.0`
>
> 依据：[010 汇报](./reports/010.md) 第 6 节和"已知问题"

## 背景

010 把列表的返回大小降到了原来的 8.5%，第二次打开只要几毫秒，两个目标都达到了。但 010 的任务说明漏了一个指标：**生成列表本身要多久**。实测 5000 张要 6.5 秒，20000 张要 34 秒，全部在主进程里同步执行，这段时间窗口没有响应。每次进入图片库、每次导入或删除之后都要取一次列表，这个耗时不能接受。

汇报里已经说明了原因：为了和旧实现逐项一致，生成每张卡片时仍然要读取并解析那张图的 `extra_json`（平均 62 KB），逐张查询，再丰富 Tag、计算相似度数据。

## 目标

以 `npm run benchmark:data-layer` 的 5000 张数据为准：

| 场景 | 目标 |
|---|---|
| 数据没有变化时取列表（应用启动后的第一次，以及之后的每一次） | 主进程一次阻塞不超过 400 毫秒 |
| 改动了一张图（改 Tag、重命名、移入回收站）之后再取列表 | 不超过 400 毫秒 |
| 导入 100 张之后再取列表 | 不超过 1 秒 |
| 从界面发起请求到界面拿到结果（真实的 Electron IPC，不是直接调数据库函数） | 不超过 1 秒 |

20000 张时给出实测数字，不设硬指标。

## 范围

### 1. 先测量

把现在的 6.5 秒拆开：读取、解析 `extra_json`、逐张查询、丰富 Tag、计算相似度、组装各占多少。写进汇报，后面的做法以测量为依据。

### 2. 允许的做法

- **派生数据的缓存表**：允许新增**一张**表，按图片 id 保存生成卡片所需的、已经算好的内容。它必须满足：
  - 是纯粹的派生数据，随时可以整张删掉重建，删掉后结果不变（有测试）；
  - 用 010 已有的脏标记判断哪些行要重算；旧版本应用写入之后，新版本打开时结果仍然正确（照 010 的做法，用真实的旧版引擎验证一次）；
  - 不改动任何已有的表和字段，不改动已有数据；
  - 翻译词典变化后结果仍然正确：译文和分类来自词典，相似度的权重依赖分类，不要把会随词典变化的内容缓存成过期的。
- **主进程内存里的缓存**：同一次运行中可以保留算好的结果，写入后只更新受影响的图片。
- **缩小返回内容**：界面端只用分组键来比较是否相等。可以把长的指纹字符串换成更短的稳定标识或做去重，前提是分组结果、封面的读取和设置仍然和现在逐项一致（010 的一致性测试继续通过，不许放宽）。
- 合并逐张查询。

### 3. 不允许

- 不把数据库操作移出主线程（另行评估）。
- 不改变两个新接口对外的含义。字段可以调整，但要在汇报里列出，并同步更新 `src/shared/` 的类型和 010 的一致性测试。
- 不改界面。

### 4. 首次建立缓存

升级后第一次打开要为所有图片建立缓存，这是一次性的。把它的耗时测出来写进汇报。如果 5000 张超过 3 秒，说明能不能分批进行、分批期间列表接口怎么表现；不要自己加界面上的进度提示，写进汇报由设计决定。

### 5. 测量工具

在基准里加上上面表格的四个场景。第四个场景要在真实的 Electron 里测（可以放进 `verify:app` 之外的单独命令，不进 CI 的默认流程）。

## 验收标准

1. `npm run format:check`、`npm run typecheck`、`npm test`、`npm run build`、`npm run verify:app` 全部通过。
2. 010 的一致性测试、补算测试全部保留并通过；新增"删掉缓存表后结果不变""词典变化后结果正确""旧版引擎写入后结果正确"的测试。
3. 四个场景的实测数字写进汇报，和 010 的数字并排。达不到目标时说明卡在哪里，不要用改变结果来换速度。

## 汇报要回答的问题

1. 原来的 6.5 秒花在哪里？
2. 四个场景各是多少？首次建立缓存要多久？
3. 缓存里存了什么、没存什么？词典变化时怎么保证不过期？
4. 用户退回旧版本再升级回来，会发生什么？
5. 接口的字段有没有变化？
