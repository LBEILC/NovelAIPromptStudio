>
> 执行者：工程负责人
>
> 分支：`rebuild/ui-1.0`
>
> 依据：CI 运行（提交 `5d9f560`，012b 之后）。012b 修的动效问题已经不再出现，验收能跑到很后面了，但四个组合仍然各有一两条失败。

## 现象

| 组合 | 失败 |
|---|---|
| Windows + Node 24、macOS + Node 22 | `electron/acceptance/library.js:428` 等待超时：从图片库"在工作台打开"后点开工作台的复制菜单，等不到"复制全部 Prompt"这一项 |
| Windows + Node 22 | 两次 `Renderer evaluation timeout: (async () => {`，日志里看不出是哪一步 |
| macOS + Node 22、macOS + Node 24 | "分页切换保留 AI 草稿"（009b 正在处理，这里不用管） |

**2026-10-12 更新（提交 `aca12e1` 的 CI）**：macOS 两个组合已经全部通过，"分页切换保留 AI 草稿"在四个组合上都通过了。Windows 两个组合各剩一条失败，是同一条：`electron/acceptance/library.js:428` 的等待超时（"图片库·正常动效"，477 条通过、1 条失败）。`Renderer evaluation timeout` 这次没有出现。

设计负责人读脚本的初步判断（需要核实，不要当成结论）：第 421 到 427 行在标题栏切到"工作台"之后，立刻去点 `.workbench-header-actions` 里最后一个带菜单的按钮，没有等图片在工作台里打开完。这时按钮可能还不可用，或者最后一个带菜单的按钮还不是复制菜单，点击就落空了。009b 在本机也碰到过一次同样的超时。注意这里是旧的工作台页面，013 会把它整页换掉：修法以"脚本先等到可以操作"为主；如果查出来是旧工作台本身会丢点击，写进汇报，不用为旧页面做大的改动。

这些在本机都是通过的。从 009a 开始，每次推送都是"本机全过、CI 上换一条失败"，说明问题不在某一条断言，而在于**本机比 CI 快得多，时序上的假设在本机暴露不出来**。这次要解决的是这个根本问题。

## 范围

### 1. 在本机模拟慢机器

给验收脚本加一个"慢机器"模式：用调试协议把渲染进程的 CPU 放慢（例如 4 倍和 6 倍），主进程里读写磁盘的操作也相应加上延迟。命令形式照 012b 的"减少动态效果"那一轮。目标是让 CI 上出现过的这几类失败能在本机复现出来。

先用它复现上面表格里的前两类，写进汇报。复现不出来的，说明还差什么条件。

### 2. 修掉暴露出来的问题

- 是验收脚本的问题（点了还没出现的元素、等的条件不对、期限按本机的速度定的）：改脚本。操作之前先等目标元素出现并可以操作。
- 是产品的问题（慢的时候会丢操作、状态错乱、界面卡住超过合理时间）：修产品，并写进汇报。
- 界面反馈类的期限（009a 的 200 毫秒、100 毫秒）是产品的要求，不要放宽；它们在慢机器模式下按放慢的倍数折算。等待类的期限（等页面切换、等数据加载）可以按环境放宽，但要有上限，并且在超时信息里写明等了多久。

### 3. 超时的时候要看得出是哪一步

- `Renderer evaluation timeout` 这类错误要带上当前的检查分类、上一条通过的断言、正在执行的操作说明。
- 任何等待超时，自动存一张当时的截图和相关区域的结构摘要（元素的角色、名称、是否可见，不存用户数据），和检查清单一起上传。
- CI 里即使验收失败，检查清单和截图也要能上传成功。现在失败后"Upload application screenshots""Upload packaged acceptance"两步因为没有文件又报了一次错，把真正的失败原因盖住了：没有文件时这两步应该跳过，不算失败。

### 4. 让验收跑得快一点

现在全套验收 788 条，深浅两个主题各跑一遍，一轮两分多钟，而且还会随着工作台迁移继续变长。之前的任务说明里常常要求"连续跑 5 次"，一个任务光验收就要十几分钟，中途碰上一次无关的偶发失败还要从头再数（用户 2026-10-11 指出这是过度防御）。改成：

- **可以只跑一部分**：`verify:app` 支持按分类运行（例如只跑"设置·AI 服务"或"图片库"），启动和准备数据只做需要的部分。修某一处时序问题时，只把相关的那一部分重复跑，几秒到十几秒一轮。
- **和主题无关的断言只跑一遍**：数据、键盘操作、复制的内容这类断言在一个主题下跑；只有和外观有关的（颜色、对比度、字体、截图）在深浅两个主题下都跑。逐条标出属于哪一类，拿不准的算两个主题都跑。目标是全套时间降到现在的六成以下，把实际数字写进汇报。
- **不再用"连续跑很多次"来证明稳定**。靠第 1 节的慢机器模式：它是确定地把时序拉开，比碰运气有效。

### 5. 以后的规矩

写进 `doc/automated-acceptance.md`：改动界面或验收脚本的任务，交付前本机跑全套一遍、慢机器模式一遍、减少动态效果一遍；修偶发失败的任务，另外把相关的那一部分在慢机器模式下重复跑 10 次。不要求全套连续跑多次。碰到和本任务无关的失败，记进汇报，不要为它重跑。CI 里只在一个组合上加跑慢机器模式（避免把 CI 时间翻倍），其余组合照常。

## 验收标准

1. `npm run format:check`、`npm run typecheck`、`npm test`、`npm run build` 通过。
2. `npm run verify:app` 全套：普通模式、慢机器模式（4 倍）、慢机器模式（6 倍）、减少动态效果各 1 次，0 失败。出过问题的那两部分（图片库到工作台的复制、Windows 上超时的那一步所在的部分）在慢机器模式下各重复 10 次。通过数和耗时写进汇报。
3. 人为制造一次等待超时，确认截图和结构摘要生成了，错误信息里有分类和操作说明。

远端 CI 由设计负责人推送后确认。本机 8766 端口上有设计负责人的界面稿预览服务，不要占用或关闭它。
