# 005 把数据引擎换成 node:sqlite

> 阶段：[重构计划](../rebuild-plan.md) 阶段 1
>
> 执行者：工程负责人
>
> 依据：[数据层基线与选型报告](../research/data-layer.md)（任务 003）

## 目标

把 `electron/database.js` 底层的 `sql.js` 换成 Node 内置的 `node:sqlite`，让写入变成增量的。

**对外接口不变。** `openDatabase()` 返回的函数名、参数、返回值的形状都保持原样，调用它的代码（主进程、导入、Tag 标注等）不需要改。图库列表仍然一次全量返回，这一点留给下一个任务。

用户的数据是这次任务里最重要的东西。任何一步拿不准，停下来写进汇报，不要自己设计一个方案直接上。

## 必须满足的结果

### 1. 旧数据原样可用

- 现有用户的 `studio.sqlite` 直接打开就能用，不需要用户做任何操作，不出现任何迁移界面。
- 不删除、不修改任何当前代码不再使用的表（见任务 003 列出的 12 张遗留表）和没有对应图片的 `generation_metadata` 行。
- 第一次用新引擎打开一个旧文件之前，先原样复制一份备份，文件名与现有的 `studio.pre-phase2.sqlite` 区分开，并且只创建一次。复制必须发生在新引擎打开这个文件之前。备份失败时不继续打开，按现有的"数据库无法打开"的方式报错。
- 现有的 `studio.pre-phase2.sqlite` 逻辑保持原样。

### 2. 应用关闭后，数据库仍然是一个完整的单文件

这是为了三件事：用户手动复制 `studio.sqlite` 做备份时不会丢数据；资源库迁移、演示环境等假设"数据库是单个文件"的代码继续成立；用户万一退回旧版本，旧版本还能读到全部数据。

实现方式由你决定并说明理由，例如：

- 不用 WAL，用回滚日志；或者
- 运行时用 WAL，正常退出时做完整的 checkpoint 并切回非 WAL 模式。

无论哪种，都要回答：应用被强制结束或崩溃之后，磁盘上是什么状态？新版本再次打开能否完整恢复？旧版本打开会怎样？把结论和证据写进汇报【实现时核实】。

写入的可靠性不能低于现在：一次成功返回的写入，在断电后不能丢。

### 3. 写入是增量的、原子的

- 每个会修改数据的接口，要么全部成功、要么全部不生效。一次调用里涉及多条语句的（例如插入一张图片连同它的 Tag 和元数据、收藏集成员变更、批量更新）放在一个事务里。
- 批量导入时，不要每张图单独提交一次；但也不要让一次失败导致整批已经成功的图片回滚。具体的批次边界由你决定并说明。
- `persist()` 保留为一个接口，避免调用方报错，但不再导出整库。它现在的含义是什么（什么都不做，还是触发一次 checkpoint）写进汇报。

### 4. 连接有明确的生命周期

- 增加关闭连接的接口。应用退出时关闭；测试结束时关闭后再清理临时目录（Windows 上不关闭就删不掉文件）。
- 更新安装前要保证数据已经落盘并关闭连接。检查 `electron/updates.js` 和主进程里退出、重启安装的路径。

### 5. 打开速度

`backfillPromptFingerprints()` 现在每次打开都会遍历全部图片重新计算。改成只处理确实需要补算的行。**补算的结果必须和现在完全一致**：用测试证明，对同一个数据库，新旧两种做法得到的指纹逐行相同。做不到完全一致就保持原样，并在汇报里说明原因。

## 测试

- 现有测试的意图都要保留。因为引擎变了而必须调整的测试（例如比较备份文件字节的断言），逐个列进汇报并说明原因。
- 新增一个**旧文件升级测试**：在移除 `sql.js` 之前，先用现有代码生成一个小的数据库文件（包含当前全部表、12 张遗留表各几行、几条孤立的元数据行），作为固定的测试文件提交进仓库（体积控制在几百 KB 以内，内容是合成数据）。测试用新引擎打开它的副本，验证：备份已创建且与原文件逐字节相同、全部表和行都在、读出的图库内容与预期一致、修改后关闭再打开数据仍在、关闭后目录里只有主数据库文件和备份。
- 新增：一次调用中途失败时没有留下半截数据；强制不关闭连接就结束进程后，再次打开数据完整（可以用子进程模拟）。
- 把 `npm run benchmark:data-layer` 改成测量**产品里真正的实现**，在 1000、5000、20000 三个规模下重新跑，数字写进汇报，和任务 003 的基线并排。
- CI 的 Windows 和 macOS 都要跑到旧文件升级测试，并保留"在 Electron 主进程里实际加载 `node:sqlite`"的检查。

## 收尾

- 从依赖里移除 `sql.js` 和 `better-sqlite3`，删除只为对比 `better-sqlite3` 而存在的研究代码。确认打包配置里没有残留的相关规则。
- 更新 `doc/demo-profile.md` 等文档里关于数据文件的描述（如果实现方式让目录里多出了文件）。

## 手动验证

这次改动影响启动和真实数据，需要用户在 Windows 上用自己的图库验证。按 `AGENTS.md` 的流程写一份手动验证文档，至少包括：

1. 升级前先手动复制一份数据目录作为额外保险（写清目录位置和做法）。
2. 启动后图库内容、收藏集、回收站、Tag 翻译都在。
3. 备份文件已经生成。
4. 修改一个 Tag 的翻译、导入几张图片、删除并恢复一张图片，重启后都还在。
5. 关闭应用后，数据目录里的文件符合"完整的单文件"的要求。
6. 修改 Tag 时界面不再卡顿（和升级前对比的主观感受即可）。

不要自己执行这些步骤，也不要声称已经验证。

## 不做

- 不改 IPC 接口和 `src/` 下的任何界面代码。
- 不改表结构，不加新表，不清理遗留表和孤立行。
- 不做图库列表的分页或瘦身，不把数据库操作移到别的线程。这些是下一个任务。
- 不把 `electron/` 迁到 TypeScript。
- 不读取、不修改用户真实的数据目录。所有测试都在临时目录里进行。

## 验收标准

1. `npm run format:check`、`npm run typecheck`、`npm test`、`npm run build` 全部通过。
2. 旧文件升级测试、中途失败测试、未关闭连接后恢复的测试都在，并且通过。
3. 仓库里不再有对 `sql.js` 的引用（文档里的历史记录除外）。给出检查命令和结果。
4. 汇报里有三个规模下新实现的实测数字。
5. 手动验证文档已经写好，放在 `doc/` 根目录。
6. 打一个不签名的 Windows 目录包并启动一次无窗口的检查，确认打包后的应用能打开数据库。
