# 010b 改一条词典不该重建整个图库缓存；首次建立缓存不冻结窗口

> 阶段：[重构计划](../rebuild-plan.md) 阶段 4，012（图片库界面）的前置
>
> 执行者：工程负责人
>
> 分支：`rebuild/ui-1.0`
>
> 依据：[010a 汇报](./reports/010a.md) 第 6 节和"已知问题"

## 背景

010a 让取列表在数据没变时很快（5000 张 363 毫秒，热的时候 23 毫秒）。剩下两种情况仍然会同步重建全部卡片，窗口在此期间没有响应：

1. **翻译词典有任何实质变化**：5000 张要 7.1 秒。而改词典是日常操作，在工作台里翻译一个新 Tag、改一条译文、改一个分类都会触发。改完回到图片库就要卡这么久，不能接受。
2. **升级后第一次建立缓存**：5000 张 6.2 秒，20000 张 27 秒。只发生一次，但发生时窗口是冻住的，用户会以为软件卡死了。

## 范围

### 1. 词典变化只影响相关的图片

目标（5000 张的基准数据）：

| 场景 | 目标 |
|---|---|
| 改一条只出现在一张图里的 Tag 的译文或分类，然后取列表 | 不超过 400 毫秒 |
| 改一条出现在八成图片里的 Tag 的分类（例如 `1girl`），然后取列表 | 不超过 1.5 秒 |
| 一次导入 200 条词典（其中 20 条被图库里的图用到），然后取列表 | 不超过 1.5 秒 |
| 词典的时间戳、展示名之类不影响结果的变化 | 不重算（010a 已有，保持） |

做法由你决定，例如只让包含这些 Tag 的图片失效，或者不把随词典变化的内容存进持久缓存、读取时再套用。结果必须和全量重算逐项一致，010 和 010a 的测试全部保留。旧版本应用直接改词典之后，新版本打开时结果仍然正确。

基准数据里要有这两种 Tag（只出现一次的、出现在八成图片里的）；现有的合成分布不满足时补充，并在汇报里说明。

### 2. 首次建立缓存分批进行

- 建立缓存时分批处理，批与批之间让出主线程。主线程单次阻塞不超过 100 毫秒（5000 张的基准数据）。
- 建立期间到达的列表请求等待同一个建立过程，完成后拿到完整结果，不返回半份列表。
- 建立期间发生的写入（导入、改名、删除、改词典）不能丢，也不能让结果出错：完成后的结果要和"全部写入发生之后再全量重算"一致。有测试。
- 建立过程中应用被关闭或崩溃，下次打开能接着做或重新做，不留下错误的缓存。有测试。
- 向界面发进度：一个只读的事件，内容是已完成的张数和总张数。在 `src/shared/ipc.ts` 里有类型。界面怎么显示由 012 做，这次不改界面。
- 上面第 1 点里如果还存在需要重建很多卡片的情况，也走同一套分批流程。

数据没有变化、缓存已经建立时，取列表的速度不能比 010a 慢（5000 张：重开后第一次不超过 400 毫秒，热的时候不超过 100 毫秒）。

### 3. 不做

- 不把数据库操作移出主线程。
- 不改界面，不改两个接口对外的含义。
- 不新增表（010a 的缓存表可以调整结构，它是派生数据）。

## 验收标准

1. `npm run format:check`、`npm run typecheck`、`npm test`、`npm run build`、`npm run verify:app` 全部通过。
2. 上面每个场景在基准里有带阈值的检查，5000 张全部通过；20000 张给出实测数字。
3. 建立期间写入、建立中途退出的测试都在并通过。
4. 用真实的旧版引擎再验证一次"旧版改词典、导入图片后升级回来"。

## 汇报要回答的问题

1. 词典变化现在是怎么处理的？四个场景各是多少？
2. 首次建立缓存：总时长、主线程单次最长阻塞、期间界面还能不能操作。
3. 建立期间的写入是怎么保证不丢、不错的？
4. 进度事件的名字和内容。
