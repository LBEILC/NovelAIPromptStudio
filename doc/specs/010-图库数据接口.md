# 010 图库数据接口：精简列表、按需详情、启动不再全量重算

> 阶段：[重构计划](../rebuild-plan.md) 阶段 4，图片库迁移的前置
>
> 执行者：工程负责人
>
> 分支：`rebuild/ui-1.0`
>
> 依据：[数据层报告](../research/data-layer.md)、[005 汇报](./reports/005.md) 的基准与"已知问题"

## 背景

任务 005 把写入变快了，剩下两个瓶颈：

1. **列表太大**：`loadLibrary` 一次返回每张图的全部内容，包括平均约 62 KB 的 `extra_json` 和约 21 KB 的 `prompt_structure_json`。1000 张约 139 MB，5000 张约 695 MB，20000 张约 2.8 GB，全部经过 IPC 传给界面。
2. **启动慢**：`backfillPromptFingerprints()` 每次打开都逐张解析元数据、重算指纹。5000 张约 5 秒，20000 张约 24 秒。

而图片库的网格、筛选、搜索、分组实际只用到其中很小一部分字段：名称、时间、收藏与删除状态、尺寸、模型、Vibe 指纹、各种 Prompt 指纹、Tag 的文字/译文/分类、计算 Base Prompt 相似度用的数据，以及搜索需要的原始 Prompt 文本。完整的元数据和 Prompt 结构只在选中某张图、打开大图预览或送入工作台时才需要。

## 范围

### 1. 新的列表接口

新增一个返回"卡片记录"的接口，只包含图片库网格、筛选、搜索、分组、排序需要的字段。

- 逐个核对 `src/lib/galleryFilters.js`、`src/lib/galleryGrouping.js`、`src/lib/galleryCollections.js`、分组 Worker 和图片库页面现在实际读取的字段，列出清单写进汇报，卡片记录只包含这些。
- Base Prompt 相似度现在依赖 `prompt_structure` 和 `metadata`。改为在主进程里预先算好它需要的数据随卡片记录一起返回，界面不再需要完整结构。**分组和相似度的结果必须和现在完全一致**，用测试证明（对同一份测试数据，新旧两条路径算出的分组逐项相同）。
- 搜索范围要包括原始 Prompt 文本里的词（新设计里搜索会覆盖段落）。
- 回收站、收藏视图和现在的行为一致。

### 2. 按需详情

新增一个按 id 取单张图完整记录的接口，返回内容与现在 `loadLibrary` 里单条记录完全相同（字段和形状都一样），供详情栏、大图预览和送入工作台使用。

### 3. 启动时不再全量重算

用现有的 `app_meta` 表（键值表）记录"指纹算法的版本"和必要的标记，让打开数据库时只处理确实需要补算的行。约束：

- **不新增表和字段。**
- 结果必须和全量重算完全一致。必须考虑这几种情况并逐一有测试：新导入的行；改名或修改过的行；旧版本应用写入的行（用户退回旧版、用旧版导入几张图、再升级回来）；指纹算法版本升级时全部重算。
- 如果你发现在不新增字段的前提下做不到完全一致，停下来，把原因和你建议的最小改动写进汇报，保持现在的全量重算。

### 4. 旧接口

`loadLibrary` 保持不变，旧的图片库界面继续用它，直到下一个界面任务把图片库迁移到新接口。

### 5. 测量

在 `npm run benchmark:data-layer` 里加上新接口，1000、5000、20000 三个规模下记录：打开耗时（第一次和第二次打开分开记）、列表接口耗时与返回大小、取单张详情耗时、主进程一次最长阻塞时间。和 005 的数字并排写进汇报。

目标：5000 张时列表返回大小不超过现在的十分之一，第二次打开不超过 1 秒。达不到时说明卡在哪里，以及把数据库操作移出主线程能不能解决、代价是什么，但这次不做移出。

## 不做

- 不改任何界面。
- 不新增表和字段，不改已有数据。
- 不把数据库操作移出主线程。

## 验收标准

1. `npm run format:check`、`npm run typecheck`、`npm test`、`npm run build`、`npm run verify:app` 全部通过。
2. 分组与相似度一致性测试、启动补算的各种情况测试都在并通过。
3. 新接口在 `src/shared/ipc.ts` 里有类型。
4. 汇报里有三个规模的测量结果，以及卡片记录的字段清单与每个字段的使用位置。

## 汇报要回答的问题

1. 卡片记录有哪些字段？平均每张多大？
2. 5000 张时，第二次打开和列表接口各要多久？目标达到了吗？
3. 启动补算是怎么判断哪些行需要处理的？哪种情况最容易出错，测试是怎么覆盖的？
4. 把数据库操作移出主线程，你的评估是什么？
